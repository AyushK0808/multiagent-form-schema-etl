%  ABSTRACT
% -----------------------------------------------------------------------
\begin{abstract}
Semi-structured data may contain many types of structured elements such as names and addresses whose values need to be accurate, fit into their respective schemas, and be traceable to the original page they were extracted from. In this paper, we develop a schema-aware data-extraction approach that includes two independent extractors which run in parallel. The first, a Donut extractor does not rely upon OCR (Optical Character Recognition). This is accomplished through the use of a Deterministic Evidence-Based Fusion Policy where each possible answer is determined based upon the accuracy of each possible answer to match up to each field. The second, called the OCR-Grounded LLM (Large Language Model), relies upon OCR as part of it’s process. These two extractors reconcile at the field level using the same Deterministic Evidence-Based Fusion Policy. The schemas for each field are also derived from an Embedding-Based Registry. In addition to the above described structure, we also describe our implementation of a lightweight LoRA (Low-Rank Adaptation) Adapter for LayoutLMV3 for each document style. Each of these adapters update only a very small percentage of LayoutLMV3's total number of parameters, but still result in significant improvements to Macro-F1 over the frozen backbone results on all four document styles such as receipts/invoices/forms and multi-domain pages. As well, there was very little variance between seeds. Overall, when we evaluate our overall extraction framework  on three different datasets : SROIE, CORD and a synthetic multi-page contract dataset, we find that the overall extraction framework performs better than either of it's individual components on CORD and performs equal or slightly better than a state-of-the-art local Vision-Language Model (VLN) on the multi-page contract dataset. Additionally, the VLN outperformed us on SROIE. Finally, we found that grounding  is the most important component of our fusion policy and helps prevent a large increase in "hallucinated" answers (i.e., answers that did not exist in the input) caused by the OCR-Free nature of Donut.
\end{abstract}a

%  I. INTRODUCTION
% -----------------------------------------------------------------------
\section{Introduction}

Semi-structured documents generated through business processes include receipts, invoices, forms and contracts; they include both structured layouts and natural language. Since each version of a field may appear in different locations depending on vendor and country, using rule-based extraction methods based on positional information does not work when transferring those rules between environments.

Layout aware models such as LayoutLM \cite{layoutlm}, LayoutLMv2 \cite{layoutlmv2} and LayoutLMv3 \cite{layoutlmv3}, have been used in place of traditional rule-based methods. More recently, OCR free models such as Donut \cite{kim2022donut}, have allowed for extraction of values from a schema provided at run-time without requiring task specific training. However, there is still an issue that none of these models provide an anchor point on the original document. In other words, a well formed response can be returned which will match the required format but actually contains a non-existent value. Additionally, since a single model call will return all possible responses, the caller has no way to determine how or where a particular response came from.

To help address this we developed a framework that views extraction as a reconciliation process. Our framework uses two complimentary extractors running in parallel, one extractor is based on an OCR free Donut branch, and the second is based on an LLM/OCR branch that provides a fall-back to a VLM for missing values. A deterministic policy is then applied to make a decision regarding every field. This decision is made based upon evidence: Does the extracted value have a basis in the OCR text? Is the extracted value consistent with the expected data-type for the field? Has the same extracted value been reused across multiple fields? Is the extracted value physically located within the location designated for the field. Never is model confidence utilized as part of making a decision about a field. Both the decision and the justification behind that decision are recorded as metadata for each field,therefore every produced output value can be audited.

In this paper we have introduced a field-level fusion policy to generate results without OCR, using text as established by OCR and with an audit trail for each field extracted. Style specific LoRA adapters for LayoutLMv3 (via a unified six-class layout labeling scheme) are used for the policy and trained to output the correct class with a potential macro-F1 improvement of up to 0.19 (during testing), updating only 0.94\% of the parameters in the frozen model. We also propose an embedding-based schema registry for eliciting and filtering out document types unknown to the registry from the set of examples to query the schema agent, likely avoiding wrong schema prediction. We perform an extensive evaluation of the system using the SROIE and CORD datasets, as well as a randomly generated multi-page dataset, using a locally deployed 7B VLM and measuring ablations, rule-by-rule error analysis and latency.

\section{Related Work}
\label{sec:related}

\subsection{Rule-Based and Template Extraction}

Early document extraction systems used to use hand written rules, regex and template based approaches which were tied to specific locations within pages. Declarative rule-based engines continue to be widely used by commercial vendors (due to their deterministic and explainable nature) [1] , however, there is a need to continually develop new rules for new layouts and/or new versions of documents. As this creates additional costs through increased numbers of templates our rule-based approach maintains the determinism of declarative rule-based engines while applying these to the output of trainable extractor algorithms instead of directly to page location coordinates.
\subsection{Layout-Aware Pre-Trained Models}


LayoutLM [6] utilizes two dimensional position encoding of OCR tokens and adds it to a BERT style neural network encoder; LayoutLM v2 [8] includes additional visual features and spatially-aware self-attention mechanisms; LayoutLM v3 [10] incorporates both text-image masking and replaces the CNN backbone with linear patch embedding; BROS [5] encodes relative positioning of text blocks; LiLT [4] decouples a language independent layout stream into a separate layer from the various text encoding layers allowing for flexibility in combining different types of text encoders; GeoLayoutLM [11] provides geometric pretraining for extracting relations. Additionally, FormNet [9] provides a method to model explicit label-value structure utilizing graph convolutional networks and rich attention mechanisms to restore structural information when transforming a structured format document into a serialized flat-file format.

All of these models have been trained on datasets including FUNSD [14] for forms and CORD [16], SROIE [17] for receipts, along with regional level corpora like DocLayNet [15]. Each of these models depends upon an Optical Character Recognition (OCR) engine (such as Tesseract [18]) which inherits its accuracy limitations. The addition of a task-specific classification head requires new training data for each unique document schema.

\subsection{OCR-Free and Generative Document Models}

Models like Donut \cite{kim2022donut} and Pix2Struct \cite{lee2023pix2struct} do not have an OCR step in them because they both get the information from the image instead. However, when you run those models through your data they will produce whatever text they think should go there even if it wasn't on the actual document. 
\subsection{LLM and VLM Extraction}

Large language models (LLMs) don’t require a lot of annotation to find out what entities and fields exist in a given piece of text. For example, GPT-NER \cite{gptner2025} takes traditional sequence labelling tasks (like identifying names or locations in a sentence), and turns them into text generation. In regards to documents, typically the OCR text is fed into LLMs as a prompt. This eliminates all the layout of the original document, and only allows for short single pages of documents to be inputted. That leaves large, multi-page documents still as challenging as ever. There are a few exceptions though such as CUAD \cite{cuad2021}, which has clause level annotations for contracts, and Kleister \cite{stanislawek2021kleister}, which uses key-information labels for long documents with many complexities.

Agentic methods like ReAct \cite{react2023} allow the model to perform a chain of "thinking" then "doing" and to update intermediate outputs, which might allow it to correct errors. But a chain of single-model calls produces an answer that cannot be easily understood in terms of its final value and reasoning that led to it. VLMs, like Qwen2.5-VL \cite{bai2025qwen25vl} on the page image and target output schema are reasonable single-call extractors for receipts, but they only produce a single output call that yields one value per field, no record of how that output was arrived at, and no accounting for the differences among alternative readings of the page. In this sense, the local VLM is both the baseline and the vision fallback in the OCR-LLM branch.

\subsection{Combining Multiple Extractors}

Combining outputs from multiple systems is a well studied paradigm, as exemplified by ROVER \cite{fiscus1997rover} which matches the output of multiple speech recognition systems and then runs a voting scheme per word (with weights based on confidence if available). Such mechanisms generally assume that the rankers are of roughly equal quality or calibrated scores. These assumptions do not hold for the OCR-free generator, which makes errors different from the OCR-text extractor and which does not have usable confidence measures \cite{guo2017calibration}. The audit record of the relative performance of the fuse and rule-based extractor is similar to a line of work on data provenance, which is concerned with the space between "the reason why a value appears in the output, and the reason why this value was output" \cite{buneman2001provenance}.

\subsection{Schema Matching and Retrieval}

Matching of an incoming set of fields to a known schema is a classical task of database systems. Rahm and Bernstein \cite{rahm2001schema} distinguish matchers based on whether they rely on the element names, on instances, or structure, and how multiple matchers are combined. Embedding methods such as Sentence-BERT \cite{reimers2019sbert} enables to measure the similarity of element descriptions and element names in a common space using cosine similarity. This seems to be a reasonable approach to schemas for which field names are source-specific. Document extraction systems, however, usually assume a fixed schema for each model, and do not evaluate schema matching based on whether it can turn away unknown document types.

\subsection{Parameter-Efficient Adaptation}

Adapters \cite{houlsby2019adapters} insert small trainable bottleneck modules inside a frozen network, while LoRA \cite{hu2022lora} learns low-rank modifications to attention matrices to be inserted into a frozen pre-trained model after training. Both methods have been mostly studied in language models. Their study on layout-aware document encoders in documents of different styles and multiple label spaces, for which a single frozen base feeds multiple style-specific adapters, has been limited.

\section{Identified Gaps and Problem Statement}
\label{sec:gaps}

\subsection{Identified Gaps}

Types of information extraction tools like layout-aware, OCR-free, and generative, have previously been analyzed independently. When these three models were used together as part of an overall pipeline, researchers typically relied on either "voting" or "confidence-weighted" models to determine when to trust one model over another. The issue is that OCR-free models do not generate "scores" for their predictions in the same way that other models do. Researchers have also historically compared the output of OCR-free models to the OCR-based versions of the same document -- and tracked what portion of the document was extracted by which extractor -- but this has rarely been documented in prior research. In terms of how data extraction pipelines process documents at runtime, there has historically been little attention paid to schema inference or validation on unseen document formats -- nor to evaluating the performance of such pipelines against a baseline metric involving a single invocation of a Vision-Language Model (VLM) per page.

\subsection{Problem Statement}

Input. Document D as a PDF input that is segmented into blocks of either native or OCR text B. Typed fields f1 through fn comprising of constraints - provided or (inferred if absent) retrieved from a registry (mathcal R) of constraints. Output. For each field, a value v_i (or null); a confidence level c_i in [0..1]; and an audit log entry a_i. Each value v_i will correspond to some block within D; satisfy all constraints associated with it (and include a flag indicating whether or not it does so); be determined deterministically based upon the output of a particular path through a branch; and if necessary, be generated using vision fallback.

\textbf{Orchestration.} Eight stages depicted in Fig.~\ref{fig:system_architecture}. The first stage (ingestion) populates stage~1. Stage~1 is for choosing the LoRA layout adapter (dashed). The two parallel branches of extraction in stage~2 are merged at stage~3. All the stages share a state (document blocks, rendered page images, chosen adapter, extraction bundle for both branches, fused fields and their audit, schema resolved, validation results, storage key, errors accumulated). Stages manage their own exceptions. Therefore, if one of the stages fails, the state for later stages remains partial. Adapters group choice is made according to the identified/retrieved schema name. The adapters assign a label to the layout areas. Field extractors use spatial info directly from the OCR bounding boxes.
\subsection{Document Ingestion with OCR Fallback}

The ingestion phase converts the PDF into blocks (with page number, text, bounding box (x_0,y_0,x_1,y_1), confidence and a tag (source, native or OCR)). Text reading is performed using PyMuPDF. Page with less than 20 characters or 5 words are rendered (at $2\times$ and halved if over 5000 pixels) to feed Tesseract. Word level confidences are stored for fusion layer.

\noindent\rule{\columnwidth}{0.4pt}
\begin{algorithmic}[1]
\STATE \textbf{Input:} OCR-LLM value $v_O$, confidence $c_O$; grounded Donut value $v_D$, confidence $c_D$; floor $\delta$; field type $\tau$
\IF{$v_O$ and $v_D$ are both null}
    \STATE \textbf{return} null
\ELSIF{$v_D$ is null}
    \STATE \textbf{return} $v_O$ if $c_O \geq \delta$, else null
\ELSIF{$v_O$ is null}
    \STATE \textbf{return} $v_D$ if $c_D \geq \delta$, $v_D$ is usable and $\tau$ is not numeric; else null
\ELSIF{canonical($v_O$) $=$ canonical($v_D$)}
    \STATE \textbf{return} $v_O$ \COMMENT{agreement}
\ELSIF{field is spatially anchored}
    \STATE \textbf{return} $v_O$
\ELSIF{$v_O$ is unusable \AND $v_D$ is usable}
    \STATE \textbf{return} $v_D$ \COMMENT{evidence, not confidence}
\ELSE
    \STATE \textbf{return} $v_O$ \COMMENT{default}
\ENDIF
\end{algorithmic}

\subsection{Parallel Extraction}

Donut and OCR-LLM extractors are executed on two threads of workers and output (for each field) value, conf and spatial metadata.

\textbf{Donut branch.} Each field $f_i$ is posed as a question $q_i$ derived from its description (e.g., ``What is the invoice date?''), giving $\text{answer}_i = \text{Donut}(\text{image}, q_i)$ with confidence
\begin{equation}
    c_i^{\text{donut}} = \frac{1}{T} \sum_{t=1}^{T}
    \max_{v} \text{softmax}(s_t)_v ,
    \label{eq:donut_conf}
\end{equation}
where $s_t$ is the logit vector at generation step $t$ of $T$. Weights are loaded lazily on first use.

\textbf{OCR-LLM branch.} Text LLM takes the first 4000 characters of the document and all the fields descriptions and produces the JSON extraction. For each empty field, page image is sent to VLM along with the field. To extract fields that rely on the image: stamps, tables, signature, etc. Extracted values are associated to the OCR blocks to get bounding boxes.

\subsection{Evidence-Based Policy Fusion}
\label{sec:fusion}

The calibration of token probabilities in Donut seems quite poor, with plausible and implausible answers having a similarly narrow range of probabilities (0.9-1.0). As a result, the fusion process is based on evidential considerations, where confidence is simply a low threshold $\delta$, beneath which one value is rejected.

\textbf{Grounding.} For each output from Donut, the method looks for that output in the OCR blocks on the page. Any response that cannot be found in all blocks is thrown out. For each verified response, the confidence of the block containing the answer is used.

\textbf{Usability.} Values are considered unusable if they have not been set to the expected type of field, ie a date which does not have a four digit year or a number of the wrong type, i.e. not numeric or a number value which is not a number. They are also considered unusable if multiple fields use the same value, or an 'utterance' of greater than ten words results in a clause rather than a value.

\textbf{Decision.}  Use the value from the OCR-LLM branch unless it is unusable and the Donut value is usable. If the value from both the OCR-LLM and Donut branch is usable, Donut will only override the value of fields with spatial based fields, e.g. dates, amount, signature. For unfilled fields in the OCR-LLM branch for non-numeric fields, Donut can fill in for the field to be filled (as several incorrect values were a result of Donut-only numerical fill during development). See Algorithm~1 for the process to fill each field.

There is an additional normalization of values, including tokens within the value like a space, and the additional tokens common to boilerplate language (ex. As defined herein), in addition to cross field validations such as effective_date <= expiry_date, disclosing_party!= receiving_party. If any of these validations fail, the event is recorded as a record metadata entry, and this text is not "corrected". Additionally, each "fused" field is marked with the branch of the source element and rule that prompted its creation

\subsection{LoRA Adapter-Routed Layout Analysis}

\textbf{Dataset grouping.} Four datasets with token- or region-level layout annotations are placed into two different sets of styles. Group 1 (receipts and invoices: CORD and SROIE) comprises 1,363 pages in the training set, while Group 2 (forms and multi-domain pages: FUNSD and Doc Lay Net) has 4,954 pages in training (capped at 5k in the case of Doc Lay Net). Layout statistics of these two groups differ, indicating that each group will likely need its own adapter on a shared frozen LayoutLMv3-base. A routing system will keep the base model and a small set of most recently used adapters stored in memory, then transition between adapters with the PEFT calls load_adapter and set_adapter. (Note: Adapters will be learned to predict layout classes, not the values of the fields, so that the dataset does not reveal answers to information extraction questions in the end-to-end evaluation.)

\textbf{Unified label space.} The granularity of the datasets varies: word-level entities in FUNSD, region categories in Doc Lay Net, and receipt fields in CORD and SROIE. The datasets are grouped into one of six label types: paragraph, heading, list item, table, caption, and other. Each OCR token (detection; bounding box normalized to $[0,1000]$) in a document is given the label of the first region it falls in before it's passed to a predicate of the object label type, or is given a background label otherwise. This means supervision at the word level, region level, and document level are combined into one token-level task, meaning the two adapters are relatively directly comparable. Additionally, due to the constant base model and label set, either adapter can label any document without training, which we expect will improve transfer across groups.

\textbf{Adapter configuration.} We use LoRA on the query, key, value, and output projections with r=16, α=32 and dropout = 0.05. We use AdamW as the optimizer with learning rate 5×10−5, weight decay 0.01, cosine schedule with 6% warmup, batch size 2 and 8 accumulation (total batch size 16). We use 512 token context length and bf16 for computation. We run a maximum of 10 epochs, with early stopping using macro-F1 on the validation set (patience = 3). We output a JSON file with the full parameters for each experiment, per-epoch evaluation results and the test set evaluation results. These are then used in all layout-adapter tables and figures.
\subsection{Schema Registry, Validation and Storage}

Schemas are encoded as the mean embedding of all descriptions in all-MiniLM-L6-v2. They are likely matched using cosine similarity to a threshold σ, and then a schema agent (likely the agent responsible for fixing schema fields) (GPT-OSS-20B/120B) matches fields to schema descriptions, renames fields or creates new schemas and fixes bad fields. There is value and type checking. Bad fields are fixed and the attempt is made again, or the field takes on the default value from the schema. Valid rows are written to a SQLite database.

\section{Experimental Results and Evaluation}
\label{sec:eval}

\subsection{Experimental Setup}

All experiments were implemented using Python~3.12 on a laptop running Windows~11, using PyTorch. One NVIDIA RTX~5060 Laptop GPU (8\,GB) was used. LangChain and LangGraph were used for orchestration. SQLite was used for data storage. PEFT was used for fine-tuning.

\textbf{Layout adapters.} Each experiment was trained using seeds 13, 42 and 1234 with a consistent train/valid split. If the dataset contains an existing validation set (CORD and DocLayNet), this was used. Otherwise a 10\% random subset (seeded) was used (FUNSD and SROIE). For final results, the official test set was used. For Group~1, the CORD test set (100 pages) and SROIE test set (347 pages) was used. For Group~2, the first 834 pages of the DocLayNet test set and the FUNSD test set (50 pages) was used. The baseline trains only the token classification layer and freezes the rest of the model. All other parameters (data, number of training iterations, early stopping etc) were kept identical.

\textbf{End-to-end extraction.} The results of this evaluation were obtained from two groups of test data and three different types of input data. Each of these three different types of input data represented different styles of documents. For example, one type of input data was an invoice, another type of input data was a non-disclosure agreement (NDA), and the third type of input data was an employment contract. In addition, there were six amount fields in the second group of test data, and they were also part of invoices. Two types of test data were used. One type included 15 different documents. These documents had multiple pages. The other type contained 100 test receipts from SROIE, 50 test receipts from CORD, and all documents were randomly selected. Since there are no settings that need to be adjusted, all model stages ran locally at temperature 0. Therefore, the performance metrics shown below represent the average performance metric for all of the test data.

Neither the specialized OCR-LLM branch alone nor the pipeline are competitive at just extracting text: Donut reaches at best 0.257 F1 with 0.673 pass rate, whereas the OCR-LLM branch with visual fallback and the fusion pass 0.80--0.98.

The VLM is only one part of the whole pipeline. The VLM serves as a visual fallback of the OCR-LLM branch. The success on SROIE, which has four fields per page, indicates that visual routes could be helpful, and the logic rules from Algorithm 1 could also be used on the output of the VLM, which is the third source of evidence.

\subsection{Latency}

Timing analysis was performed for 15 documents, five from each set after the initial warm-up was thrown away, with response caching disabled. Each stage was run sequentially, and the median result plotted in Figure \ref{fig:latency}. Timing analysis of CORD VLM was omitted as Ollama seemed to have answered from its prompt cache. Fusion takes under 3 ms to complete, with OCR taking about 1.2 seconds. In addition, on the SROIE set, where the text pass saturates all fields, the entire pipeline takes 14.3 s per receipt versus 19.5 s for a single VLM call, and, on CORD set, where the text pass only fills sparse fields so vision fallback is required, the median timing of the entire pipeline is 29.7 seconds. For synthetic multi-page documents, the median timing is 24.4 seconds, 17 seconds of which is the Donut component. Running both the two branches in parallel during deployment likely restricts the extraction time to that of the slower branch rather than summing the time of the two branches.

\subsection{Schema Registry Retrieval}
\label{sec:res_schema}

\begin{figure}[t]
    \centering
    \includegraphics[width=0.7\columnwidth]{schema_registry}
    \caption{Schema retrieval precision and recall against threshold $\sigma$.}
    \label{fig:schema_pr_curve}
\end{figure}

The registry contains 8 schemas (4 synthetic document types, SROIE and CORD receipts, purchase orders and forms) and the query set 50 labelled field-name sets; 40 labelled sets describe a registered schema (exact name, two synonym renames, two subsets and two subsets with unrelated additional fields per schema) and therefore must be accepted; 10 describe an unregistered document type and must be rejected. At the operating point of $\sigma=0.70$ (Fig. \ref{fig:schema_pr_curve}), where 10 of the 50 queries are rejected to the schemas agent, precision is 1.00 and no unregistered documents are accepted, with recall at 0.575. When queries with $\sigma$ below this threshold are rejected to the schemas agent, no false acceptances are made. Precision is maintained at high levels throughout, for example at $\sigma=0.45$ precision is 0.889 with recall 0.800, with no false acceptances; false acceptances only happen at $\sigma=0.40$, and in a deployment where the agent need only call the schemas agent infrequently, could be significantly reduced further.

% -----------------------------------------------------------------------
%  VI. CONCLUSION
% -----------------------------------------------------------------------
\section{Conclusion}
\label{sec:conclusion}

The schema aware framework introduced here integrates both an OCR free extractor and an OCR grounded extractor in a deterministic evidence based field by field way. The approach contains embedding based schema registry with style dependent LoRA layout adapters. Given that each style documented has enough to avoid document routing, the approach seems to have a test macro F1 of 0.774/0.739 with trainable parameters of 0.94/4.5 MB. End to end pipeline gives test F1 of 0.980 for a multi-page synthetic set that outperforms 7B VLM. CORD strongest branch maximizes performance and all three improve on exact match rate and matches VLM. Amazingly the most effective way to avoid hallucination of values is to ground the OCR free answer in page text. At operational threshold for schema registry none of the unregistered document style will be accepted. Usual error analysis is converted into rule analysis with field by field audit record. And the analysis to bridge the gap from strongest branch on SROIE is boiled down to one clause length and form rule and this can be found in log in less than 15 minutes of experimental work.
% -----------------------------------------------------------------------
%  VII. LIMITATIONS
% -----------------------------------------------------------------------
\section{Limitations}
\label{sec:limitations}

In terms of public benchmark, we have a receipt data which are usual 100/50 document public benchmarks and we run them once each for each configuration. So we cannot test the F1 difference of 0.02. There might be some disadvantages of multi-page set. Small synthetic written by the authors. We are limited in terms of grounding by output range of the OCR engine. The most obvious is in CORD data where the output of tesseract is very sparse. We manually set policy rule, threshold for development documents which we need to re-tune in case of any new domain. E.g. in case of clause test for longer address. We are experimenting with layout adapters in isolation, we don't yet plug them into field extractors.


% -----------------------------------------------------------------------
%  VIII. FUTURE WORK
% -----------------------------------------------------------------------
\section{Future Work}
\label{sec:future}

The VLM is current fallback for OCR-LLM branch. We can plug it into policy as 3rd evidence with comparable grounding, usability tests. We might be able to avoid regression on SROIE with clause test limited to clause type fields. We might also be able to pass region labels from layout adapters to field extractors to limit region for grounding to field region. Also better OCR engine will save more Donut output for grounding. Also we will do more experiments with bigger multi-page documents with public annotations e.g. Kleister \cite{stanislawek2021kleister}, CUAD \cite{cuad2021}.
