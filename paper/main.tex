% -----------------------------------------------------------------------
%  ABSTRACT
% -----------------------------------------------------------------------
\begin{abstract}
Extracting typed fields from semi-structured documents requires values that are correct, conform to a schema and can be traced back to the page. We present a schema-aware extraction framework that runs an OCR-free Donut extractor and an OCR-grounded LLM extractor in parallel and reconciles them field by field with a deterministic, evidence-based fusion policy that records the source and the reason for every value. Donut answers are grounded in the OCR text before fusion, and field schemas are retrieved from an embedding-based registry. For layout analysis we train a lightweight LoRA adapter for LayoutLMv3 per document style; each adapter updates a small fraction of the parameters, occupies a few megabytes and clearly improves macro-F1 over a frozen backbone on both receipts and invoices and forms and multi-domain pages, with little variation across seeds. End to end, evaluated on SROIE, CORD and a synthetic multi-page contract set, the framework improves on its strongest single branch on CORD, exceeds a local vision-language model on the contract set and equals that model's exact-match rate on CORD, while the vision-language model remains strongest on SROIE. Grounding is the decisive fusion component and prevents the rise in hallucinated values that ungrounded OCR-free answers cause. Because every decision is logged, the remaining errors can be traced to individual policy rules.
\end{abstract}

% -----------------------------------------------------------------------
%  I. INTRODUCTION
% -----------------------------------------------------------------------
\section{Introduction}

Business processes produce large volumes of semi-structured documents such as receipts, invoices, forms and contracts. They combine natural-language text with layout structure, and the position of a field varies between versions, vendors and countries, so extraction rules that rely on fixed positions do not carry over.

Rule-based extraction was replaced by layout-aware models such as LayoutLM \cite{layoutlm}, LayoutLMv2 \cite{layoutlmv2} and LayoutLMv3 \cite{layoutlmv3}, and later by OCR-free models such as Donut \cite{kim2022donut}. Large language models (LLMs) \cite{gptner2025} and vision-language models (VLMs) \cite{bai2025qwen25vl} now extract fields from a schema given at run time, without task-specific training. Their outputs, however, are not anchored to the page \cite{ji2023hallucination}: a generator can return a well-formed value that the document does not contain, and a single model call gives no account of where a value came from.

We address this with a framework that treats extraction as a reconciliation problem. Two complementary extractors, an OCR-free Donut branch and an OCR-LLM branch that reads the OCR text and falls back to a VLM for missing fields, run in parallel. A deterministic policy then decides every field from evidence: whether a value is grounded in the OCR text, whether it parses as the field's type, whether it is reused across fields and whether the field is spatially anchored. Model confidence is never the deciding signal. The decision and its reason are logged per field, so every output value can be audited.

This paper makes four contributions. First, it introduces an evidence-based, field-level fusion policy that grounds OCR-free answers in the OCR text and stores an audit record for every field. Second, it trains style-specific LoRA adapters for LayoutLMv3 over a unified six-class layout label space, which improve test macro-F1 by up to 0.19 over a frozen backbone while updating 0.94\% of the parameters. Third, it provides an embedding-based schema registry whose threshold rejects every unregistered document type in our query set, handing such documents to a schema agent instead of matching them to a wrong schema. Fourth, it evaluates the framework end to end on SROIE, CORD and a synthetic multi-page set against a local 7B VLM, with an ablation, a rule-level error attribution and a latency breakdown.

%  II. RELATED WORK
% -----------------------------------------------------------------------
\section{Related Work}
\label{sec:related}

\subsection{Rule-Based and Template Extraction}

Early document extraction systems relied on hand-written rules, regular expressions and templates keyed to fixed page positions. Declarative rule engines remain common in industry because their outputs are predictable and explainable \cite{chiticariu2013rule}, but every new vendor layout or document version requires new rules, and maintenance cost grows with the number of templates. Our fusion policy keeps the auditability of rules but applies them to the outputs of learned extractors rather than to raw page positions.

\subsection{Layout-Aware Pre-Trained Models}

LayoutLM \cite{layoutlm} adds two-dimensional position embeddings of OCR tokens to a BERT-style encoder, LayoutLMv2 \cite{layoutlmv2} adds visual features and spatially aware self-attention, and LayoutLMv3 \cite{layoutlmv3} unifies text and image masking with linear patch embeddings in place of a CNN backbone. BROS \cite{hong2022bros} encodes the relative positions of text blocks, LiLT \cite{wang2022lilt} decouples a language-independent layout stream so that it can be combined with different text encoders, and GeoLayoutLM \cite{luo2023geolayoutlm} adds geometric pre-training aimed at relation extraction. FormNet \cite{lee2022formnet} models label--value structure explicitly, using graph convolutions and rich attention to recover structure that is lost when a form is serialised.

These models are fine-tuned on benchmarks such as FUNSD \cite{jaume2019funsd} for forms and CORD \cite{park2019cord} and SROIE \cite{huang2019sroie} for receipts, and region-level corpora such as DocLayNet \cite{pfitzmann2022doclaynet} supply labels for layout analysis. All of them depend on an OCR engine such as Tesseract \cite{smith2007tesseract} and inherit its errors, and each new schema needs a task-specific head and labelled data.

\subsection{OCR-Free and Generative Document Models}

OCR-free models read the page image directly and generate their output as text. Donut \cite{kim2022donut} pairs a Swin Transformer encoder with a BART decoder and is pre-trained to read text before being fine-tuned for parsing or question answering, and Pix2Struct \cite{lee2023pix2struct} is pre-trained to parse masked web-page screenshots into simplified HTML. Because their answers are generated rather than located, these models avoid OCR error propagation but can return text that does not appear on the page, and the token probabilities of modern neural networks are generally not calibrated to correctness \cite{guo2017calibration}. Posing one question per field to a model fine-tuned on DocVQA \cite{mathew2021docvqa} makes the output schema-driven without retraining; we use Donut in this way and check each answer against the OCR text before it can be used.

\subsection{LLM and VLM Extraction}

Large language models (LLMs) extract entities and fields from a prompt with little or no annotation; GPT-NER \cite{gptner2025}, for instance, recasts sequence labelling as text generation. For documents, the OCR text is serialised into the prompt, which discards most of the layout and limits the length that can be processed, so long multi-page documents remain difficult; CUAD \cite{cuad2021} provides clause-level annotations for contracts and Kleister \cite{stanislawek2021kleister} key-information labels for long documents with complex layouts. Generative extractors can also produce fluent, well-formed values that the source does not support \cite{ji2023hallucination}. Retrieval-augmented generation \cite{lewis2020rag} reduces this by conditioning the generator on retrieved evidence, but it does not check after generation that the answer is actually supported.

Agentic methods such as ReAct \cite{react2023} let a model interleave reasoning with actions and revise intermediate results. They can correct errors, but the result depends on a sequence of sampled model calls and the reason for a final value is hard to reconstruct. Vision-language models (VLMs) such as Qwen2.5-VL \cite{bai2025qwen25vl} read the page image together with a requested output schema and are strong single-call extractors on receipts. A single call, however, returns one value per field without a record of where it came from or whether another reading of the page disagrees. We use a local VLM both as a baseline and as the vision fallback inside the OCR-LLM branch.

\subsection{Combining Multiple Extractors}

Combining the outputs of several systems is well established. ROVER \cite{fiscus1997rover}, for example, aligns the outputs of several speech recognisers and votes word by word, optionally weighted by confidence. Such schemes assume members of comparable quality or calibrated scores. Neither holds for an OCR-free generator and an OCR-text extractor, whose errors differ in kind and whose confidences are not comparable \cite{guo2017calibration}. Research on data provenance distinguishes why a value appears in an output from where it was copied from \cite{buneman2001provenance}; this distinction motivates our per-field audit record, which stores for every fused value the branch it came from and the rule that selected it.

\subsection{Schema Matching and Retrieval}

Matching an incoming set of fields to a known schema is a classical database problem. Rahm and Bernstein \cite{rahm2001schema} classify matchers by whether they use element names, instances or structure, and by how several matchers are combined. Sentence embeddings such as Sentence-BERT \cite{reimers2019sbert} allow the similarity of field names and descriptions to be computed as a cosine in a shared space, which suits schemas whose field names vary between sources. Document extraction systems, however, usually assume one fixed schema per model, and schema matching is rarely evaluated for its ability to reject document types that are not registered.

\subsection{Parameter-Efficient Adaptation}

Adapters \cite{houlsby2019adapters} insert small trainable bottleneck layers into a frozen network, and LoRA \cite{hu2022lora} learns low-rank updates to the attention weights that can be merged into them after training. Both have been studied mainly for language models. Their use for layout-aware document encoders across document styles with heterogeneous label sets, where one frozen base serves several style-specific adapters, has received little study.

% -----------------------------------------------------------------------
\section{Identified Gaps and Problem Statement}
\label{sec:gaps}

\subsection{Identified Gaps}

Layout-aware, OCR-free and generative extractors have been studied largely in isolation, and where outputs are combined, voting or confidence weighting presupposes calibrated scores that OCR-free generators do not provide. Verifying OCR-free answers against the OCR text after generation, and recording for each field which component produced its value and why, have not been reported. Extraction pipelines also rarely resolve schemas at run time while rejecting unregistered document types, or compare themselves with a single VLM call on the page.

\subsection{Problem Statement}

Given a PDF $D$, turned by ingestion into OCR or native-text blocks $B$, and a schema $S=\{f_1,\dots,f_n\}$ of typed fields with constraints, supplied or resolved from a registry $\mathcal{R}$, produce for every field a value $v_i$ (or null), a confidence $c_i\in[0,1]$ and an audit record $a_i$ naming the source branch and selecting rule. Each $v_i$ must match the document, satisfy its constraints or be flagged, be supported by $B$ or an explicit vision fallback, and be a deterministic function of the branch outputs; an unregistered document type must not be matched to a wrong schema.

\section{System Architecture and Methodology}
\label{sec:arch}

\begin{figure}[t]
    \centering
    \includegraphics[width=0.86\columnwidth]{architecture.pdf}
    \caption{Pipeline architecture: ingestion, the eight orchestrator stages and the two parallel extraction branches.}
    \label{fig:system_architecture}
\end{figure}

\textbf{Orchestration.} Fig.~\ref{fig:system_architecture} shows the eight stages. Ingestion feeds stage~1, which selects a LoRA layout adapter (dashed); the two extraction branches of stage~2 run in parallel and are reconciled in stage~3. The stages share a state holding the document blocks, the rendered page images, the selected adapter, the extraction bundle of both branches, the fused fields and their audit records, the resolved schema, the validation outcomes, the storage key and any accumulated errors. Each stage handles its own exceptions, so a failure in one stage leaves a partial state that later stages can still use. The adapter group is selected from the identified or retrieved schema name; the adapters label layout regions, and the field extractors take spatial information directly from the OCR bounding boxes.

\subsection{Document Ingestion with OCR Fallback}

Ingestion turns a PDF into blocks, each with page number, text, bounding box $(x_0,y_0,x_1,y_1)$, confidence and a source tag (native or OCR). Native text is read with PyMuPDF; a page with fewer than 20 characters or five words is rendered at $2\times$ scale (halved above 5000 pixels) and passed to Tesseract, whose word-level confidences are kept for the fusion layer.

\noindent\textbf{Algorithm 1:} Deterministic field-level policy fusion\\[-4pt]
\noindent\rule{\columnwidth}{0.4pt}
\begin{algorithmic}[1]
\STATE \textbf{Input:} OCR-LLM value $v_O$, confidence $c_O$; grounded Donut value $v_D$, confidence $c_D$; floor $\delta$; field type $\tau$
\IF{$v_O$ and $v_D$ are both null}
    \STATE \textbf{return} null
\ELSIF{$v_D$ is null}
    \STATE \textbf{return} $v_O$ if $c_O \geq \delta$, else null
\ELSIF{$v_O$ is null}
    \STATE \textbf{return} $v_D$ if $c_D \geq \delta$, $v_D$ is usable and $\tau$ is not numeric; else null
\ELSIF{canonical($v_O$) $=$ canonical($v_D$)}
    \STATE \textbf{return} $v_O$ \COMMENT{agreement}
\ELSIF{field is spatially anchored}
    \STATE \textbf{return} $v_O$
\ELSIF{$v_O$ is unusable \AND $v_D$ is usable}
    \STATE \textbf{return} $v_D$ \COMMENT{evidence, not confidence}
\ELSE
    \STATE \textbf{return} $v_O$ \COMMENT{default}
\ENDIF
\end{algorithmic}

\subsection{Parallel Extraction}

The Donut and OCR-LLM extractors run on two worker threads and return, per field, a value, a confidence and spatial metadata.

\textbf{Donut branch.} Each field $f_i$ is posed as a question $q_i$ derived from its description (e.g., ``What is the invoice date?''), giving $\text{answer}_i = \text{Donut}(\text{image}, q_i)$ with confidence
\begin{equation}
    c_i^{\text{donut}} = \frac{1}{T} \sum_{t=1}^{T}
    \max_{v} \text{softmax}(s_t)_v ,
    \label{eq:donut_conf}
\end{equation}
where $s_t$ is the logit vector at generation step $t$ of $T$. Weights are loaded lazily on first use.

\textbf{OCR-LLM branch.} A text LLM receives the first 4000 characters of the document and all field descriptions and returns a JSON extraction. Each field left empty is then passed with the page image to a VLM, which recovers values that depend on the image, such as stamps, tables and signatures. Extracted values are matched to OCR blocks to obtain their bounding boxes.

\subsection{Evidence-Based Policy Fusion}
\label{sec:fusion}

Donut's token probabilities are poorly calibrated: we observed 0.9--1.0 for both correct and incorrect answers. The fusion layer therefore decides from evidence and uses confidence only as a floor $\delta$ below which a lone value is discarded.

\textbf{Grounding.} Each Donut answer is searched in the OCR blocks of its page. An answer found in no block is dropped; a supported answer takes the confidence of the block that contains it.

\textbf{Usability.} A value is unusable if it does not parse as its field type (a date without a four-digit year, a non-numeric amount), if the same value was assigned to several fields, or if it is a clause of more than ten words rather than a value.

\textbf{Decision.} The OCR-LLM value is the default, and Donut takes over only when the OCR-LLM value is unusable and its own value is usable. Spatially anchored fields (dates, amounts, signatures) keep the OCR-LLM value on conflict. A Donut value may fill a field the OCR-LLM branch left empty only for non-numeric fields, because Donut-only numeric fills were the main source of wrong values in development. Algorithm~1 gives the per-field procedure.

Fusion also normalizes values (whitespace, punctuation and boilerplate such as ``as defined herein'') and runs cross-field checks such as $\text{effective\_date} \leq \text{expiry\_date}$ and $\text{disclosing\_party} \neq \text{receiving\_party}$. Failed checks are flagged in the record metadata, not silently corrected. Each fused field is stored with its source branch and the rule that selected it.

\subsection{LoRA Adapter-Routed Layout Analysis}

\textbf{Dataset grouping.} Four datasets with token- or region-level layout annotations form two groups by document style: Group~1 (receipts and invoices: CORD and SROIE, 1{,}363 training pages) and Group~2 (forms and multi-domain pages: FUNSD and DocLayNet, 4{,}954 training pages with DocLayNet capped at 5{,}000). Their layout statistics differ, so each group gets its own adapter on a shared frozen LayoutLMv3-base. A router keeps the base model and a few recently used adapters in memory and switches between them with the PEFT calls \texttt{load\_adapter} and \texttt{set\_adapter}. The adapters predict layout classes, not field values, so their training data does not leak extraction answers into the end-to-end evaluation.

\textbf{Unified label space.} The datasets differ in granularity: word-level entities in FUNSD, region categories in DocLayNet and receipt fields in CORD and SROIE. All are mapped to six labels: paragraph, heading, list item, table, caption and other. Each OCR token, with its box normalized to $[0,1000]$, receives the label of the first annotated segment that contains its centre point, or the background label otherwise. This turns word-, region- and document-level supervision into one token-level task and makes the two adapters directly comparable: because they share the base model and the label set, either adapter can label any document without retraining, which the cross-group evaluation uses.

\textbf{Adapter configuration.} LoRA is applied to the query, key, value and output projections with rank $r=16$, $\alpha=32$ and dropout 0.05. Training uses AdamW (learning rate $5\times10^{-5}$, weight decay 0.01), a cosine schedule with 6\% warmup, mini-batch 2 with 8 accumulation steps (effective batch 16), 512-token inputs, bf16 precision, at most 10 epochs and early stopping on validation macro-F1 with patience 3. Every run writes its full configuration, per-epoch metrics and test metrics to JSON files, from which all layout-adapter tables and figures are generated.

\subsection{Schema Registry, Validation and Storage}

Each schema is stored as the averaged all-MiniLM-L6-v2 embedding of its field descriptions and retrieved by cosine similarity with threshold $\sigma$. Below the threshold, a schema agent (GPT-OSS-120B/20B) matches fields, normalizes names or synthesizes a new schema; the same agent repairs fields that fail validation. Validation checks type and value constraints; an invalid field is retried or set to its schema default. Valid records are stored in SQLite.

\section{Experimental Results and Evaluation}
\label{sec:eval}

\subsection{Experimental Setup}

All experiments ran on a Windows~11 laptop with Python~3.12, PyTorch and one NVIDIA RTX~5060 Laptop GPU (8\,GB). Orchestration uses LangGraph and LangChain, fine-tuning uses PEFT, and storage uses SQLite.

\textbf{Layout adapters.} Each configuration was trained with seeds 13, 42 and 1234 on a fixed train/validation split: the datasets' own validation splits where they exist (CORD, DocLayNet) and a seeded 10\% hold-out otherwise (SROIE, FUNSD). Official test splits were used only for final evaluation: CORD (100) and SROIE (347) pages for Group~1, and FUNSD (50) and the first 834 DocLayNet test pages for Group~2. The baseline freezes the whole backbone and trains only the token-classification head, with the same data, seeds, schedule and early stopping.

\textbf{End-to-end extraction.} We evaluate on a seeded random subset of 100 SROIE test receipts (company, date, address, total), a seeded subset of 50 CORD test receipts (six amount fields) and a 15-document synthetic multi-page set (invoices, NDAs, employment contracts, land deeds and tender instruments; 30 fields). Subsets are drawn once from the official test splits with subset seed 0, and no setting was tuned on them. All model stages run locally at temperature 0: Donut-base fine-tuned on DocVQA, Llama~3.2~3B for the text pass, and Qwen2.5-VL-7B served by Ollama (8192-token context) for the vision fallback and as the VLM-only baseline. F1 is field-level token-overlap F1 after normalization, and EM is the share of gold values matched exactly. Code, result files and figure scripts are available at github.com/AyushK0808/multiagent-form-schema-etl.

On the synthetic set every variant equals the full pipeline (0.980), so Table~\ref{tab:ablation} reports SROIE and CORD. It identifies grounding as the decisive component: removing it costs 0.031 F1 on SROIE and 0.011 on CORD, and on SROIE it lowers the median per-document F1 from 0.850 to 0.788 and nearly doubles the share of receipts scoring 0.5 or less (8\% to 14\%). Restricting Donut fills to non-numeric fields matters as well: letting Donut fill every empty field lowers CORD F1 to 0.810 and raises the hallucination rate from 0.148 to 0.192. This default was fixed before the test runs. Schema-agent repair, normalization and the spatial rule each change F1 by at most 0.002 on these short receipts. They are safeguards for long documents, where normalization and cross-field checks have more to act on.

\subsection{Latency}

We timed 15 documents (five per dataset, after one discarded warm-up) with response caching disabled, running the stages one after the other; Fig.~\ref{fig:latency} reports medians. CORD VLM timings are omitted because Ollama answered them from its prompt cache. Fusion takes under 3\,ms and OCR about 1.2\,s. On SROIE, where the text pass fills most fields, the whole pipeline needs 14.3\,s per receipt against 19.5\,s for a standalone VLM call. On CORD, where sparse OCR forces the vision fallback, the pipeline median is 29.7\,s, and on the multi-page synthetic documents 24.4\,s, of which Donut accounts for 17\,s. Running the two branches concurrently, as in deployment, bounds the extraction time by the slower branch instead of their sum.

\subsection{Schema Registry Retrieval}
\label{sec:res_schema}

\begin{figure}[t]
    \centering
    \includegraphics[width=0.7\columnwidth]{schema_registry}
    \caption{Schema retrieval precision and recall against threshold $\sigma$.}
    \label{fig:schema_pr_curve}
\end{figure}

The registry holds eight schemas: the four synthetic document types, SROIE and CORD receipts, purchase orders and forms. The query set has 50 labelled field-name sets. Forty belong to a registered schema (exact names, synonym renames, subsets, and subsets with unrelated extra fields; five per schema), and ten describe unregistered document types and must be rejected. At the operating threshold $\sigma=0.70$ (Fig.~\ref{fig:schema_pr_curve}), precision is 1.00 and no unregistered query is accepted, with recall 0.575; queries below the threshold go to the schema agent instead of being matched to the wrong schema. Precision stays high over a wide range: at $\sigma=0.45$ it is 0.889 at recall 0.800, still with no false acceptance, and false acceptances begin only at $\sigma=0.40$. A deployment that prefers fewer agent calls can therefore lower $\sigma$ substantially without accepting the wrong schema.

% -----------------------------------------------------------------------
%  VI. CONCLUSION
% -----------------------------------------------------------------------
\section{Conclusion}
\label{sec:conclusion}

We presented a schema-aware framework that reconciles an OCR-free and an OCR-grounded extractor field by field with a deterministic, evidence-based policy, together with an embedding-based schema registry and style-specific LoRA layout adapters. The adapters improve test macro-F1 over a frozen backbone to 0.774 and 0.739 at 0.94\% trainable parameters and 4.5\,MB each, and they are specialised enough to justify routing documents by style. End to end, the pipeline reaches 0.980 F1 on a multi-page synthetic set, above a 7B VLM; it improves on its strongest branch on CORD and matches the VLM's exact-match rate there; and grounding OCR-free answers in the page text is its most effective component and keeps hallucinated values in check. At its operating threshold the schema registry accepts no unregistered document type. Finally, the per-field audit record turns error analysis into rule analysis: the gap between the pipeline and its branch on SROIE traces to a single clause-length rule, which the log identifies without further experiments.

% -----------------------------------------------------------------------
%  VII. LIMITATIONS
% -----------------------------------------------------------------------
\section{Limitations}
\label{sec:limitations}

The public benchmarks are receipt subsets of 100 and 50 documents evaluated in one run per configuration, so differences under 0.02 F1 are not resolved, and the multi-page set is small, synthetic and written by the authors. Grounding can keep only what the OCR engine reads, which limits it on CORD, where Tesseract output is sparse. The policy rules and thresholds were set by hand on development documents and may need revisiting for a new domain, as the clause test on long addresses shows. Finally, the layout adapters are evaluated as a standalone component and are not yet used by the field extractors.

% -----------------------------------------------------------------------
%  VIII. FUTURE WORK
% -----------------------------------------------------------------------
\section{Future Work}
\label{sec:future}

The VLM, now a fallback inside the OCR-LLM branch, can enter the policy as a third evidence source, subject to the same grounding and usability checks. Restricting the clause test to clause-type fields would remove the SROIE regression that the audit log attributes to it. The region labels of the layout adapters can be passed to the field extractors, for example to restrict grounding to the region a field belongs to, and a stronger OCR engine would let grounding retain more of Donut's output. Finally, we plan to evaluate on long multi-page documents with public annotations, such as Kleister \cite{stanislawek2021kleister} and CUAD \cite{cuad2021}.
