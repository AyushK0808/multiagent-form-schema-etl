% -----------------------------------------------------------------------
%  ABSTRACT
% -----------------------------------------------------------------------
\begin{abstract}
Extracting typed fields from semi-structured documents requires values that are correct, conform to a schema and can be traced back to the page. We present a schema-aware extraction framework that runs an OCR-free Donut extractor and an OCR-grounded LLM extractor in parallel and reconciles them field by field with a deterministic, evidence-based fusion policy that records the source and the reason for every value. Donut answers are grounded in the OCR text before fusion, and field schemas are retrieved from an embedding-based registry. For layout analysis we train one LoRA adapter for LayoutLMv3 per document style; each updates 0.94\% of the parameters, occupies 4.5\,MB and raises test macro-F1 over a frozen backbone from 0.706 to 0.774 (receipts and invoices) and from 0.550 to 0.739 (forms and multi-domain pages), with a seed standard deviation of at most 0.008. End to end, the framework reaches token-overlap F1 of 0.801 on SROIE, 0.836 on CORD and 0.980 on a synthetic multi-page contract set. It improves on its strongest single branch on CORD, exceeds a local 7B vision-language model on the contract set (0.980 against 0.973) and equals that model's exact-match rate on CORD (0.900), while the vision-language model is strongest on SROIE (0.992). Grounding is the decisive fusion component (+0.031 F1 on SROIE) and prevents the rise in hallucinated values (0.148 to 0.192) that ungrounded OCR-free answers cause. Because every decision is logged, the remaining errors can be traced to individual policy rules.
\end{abstract}

% -----------------------------------------------------------------------
%  I. INTRODUCTION
% -----------------------------------------------------------------------
\section{Introduction}

Business processes produce large volumes of semi-structured documents such as receipts, invoices, forms and contracts. They combine natural-language text with layout structure, and the position of a field varies between versions, vendors and countries, so extraction rules that rely on fixed positions do not carry over.

Rule-based extraction was replaced by layout-aware models such as LayoutLM \cite{layoutlm}, LayoutLMv2 \cite{layoutlmv2} and LayoutLMv3 \cite{layoutlmv3}, and later by OCR-free models such as Donut \cite{kim2022donut}. Large language models (LLMs) \cite{gptner2024} and vision-language models (VLMs) \cite{bai2025qwen25vl} now extract fields from a schema given at run time, without task-specific training. Their outputs, however, are not anchored to the page \cite{ji2023hallucination}: a generator can return a well-formed value that the document does not contain, and a single model call gives no account of where a value came from.

We address this with a framework that treats extraction as a reconciliation problem. Two complementary extractors, an OCR-free Donut branch and an OCR-LLM branch that reads the OCR text and falls back to a VLM for missing fields, run in parallel. A deterministic policy then decides every field from evidence: whether a value is grounded in the OCR text, whether it parses as the field's type, whether it is reused across fields and whether the field is spatially anchored. Model confidence is never the deciding signal. The decision and its reason are logged per field, so every output value can be audited.

\noindent The contributions of this paper are:
\begin{itemize}
\item an evidence-based, field-level fusion policy with OCR grounding of OCR-free answers and a per-field audit record (Section~\ref{sec:fusion});
\item style-specific LoRA adapters for LayoutLMv3 over a unified six-class layout label space, which improve test macro-F1 by up to 0.19 over a frozen backbone at 0.94\% trainable parameters (Section~\ref{sec:res_lora});
\item an embedding-based schema registry with a threshold that rejects every unregistered document type in our query set (Section~\ref{sec:res_schema});
\item an end-to-end evaluation on SROIE, CORD and a synthetic multi-page set against a local 7B VLM, with an ablation, a rule-level error attribution and a latency breakdown (Section~\ref{sec:eval}).
\end{itemize}

%  II. RELATED WORK
% -----------------------------------------------------------------------
\section{Related Work}
\label{sec:related}

\textbf{Layout-aware models.} LayoutLM\cite{layoutlm}, LayoutLMv2\cite{layoutlmv2}, LayoutLMv3\cite{layoutlmv3} and GeoLayoutLM\cite{luo2023geolayoutlm} pre-train on text, position and image features and are fine-tuned per task on datasets such as FUNSD\cite{jaume2019funsd}, CORD\cite{park2019cord} and SROIE\cite{huang2019sroie}. FormNet\cite{lee2022formnet} and Hwang et al.\cite{hwang2021cost} model label--value structure explicitly, and PICK\cite{yu2021pick} uses graph learning over spatial structure. Layout corpora such as PubLayNet\cite{publaynet}, DocBank\cite{docbank} and DocLayNet\cite{pfitzmann2022doclaynet} supply region labels; Binmakhashen and Mahmoud\cite{binmakhashen2020} survey the task. These models need a task-specific head and labelled data per schema.

\textbf{OCR-free models.} Donut\cite{kim2022donut} and Dessurt\cite{davis2022dessurt} generate structured output directly from the page image. We use Donut fine-tuned on DocVQA\cite{mathew2021docvqa} and pose one question per field.

\textbf{LLM and VLM extraction.} Prompting methods such as GPT-NER\cite{gptner2024} extract information with little annotation but can produce unsupported outputs\cite{ji2023hallucination}, and long contracts, for which CUAD\cite{cuad2021} provides clause-level labels, remain difficult. Iterative agent methods\cite{react2023,reflexion2023,selfrefine2023} let a model revise its own output; our fusion is a single deterministic pass whose decisions can be inspected. VLMs such as Qwen2.5-VL\cite{bai2025qwen25vl} read the page image and follow a requested output schema; we use a local 7B model both as a baseline and as the vision fallback of the OCR-LLM branch.

\textbf{Parameter-efficient adaptation.} LoRA\cite{hu2022lora} trains low-rank weight updates, and He et al.\cite{he2022unified} relate adapters, prefix tuning and LoRA in one framework. Its use for layout-aware document models across document styles has received little study; we train one adapter per style and test both within and across styles.

\textbf{Gap.} Prior work studies layout-aware, OCR-free or generative extractors largely in isolation. Deterministic, auditable reconciliation of an OCR-free generator with an OCR-text extractor, inside a pipeline that also covers schema retrieval and validation, and its comparison with a direct VLM baseline, have not been reported.

\section{System Architecture and Methodology}
\label{sec:arch}

\begin{figure*}[t]
    \centering
    \includegraphics[width=0.86\textwidth]{architecture_wide.pdf}
    \caption{Pipeline architecture. Ingestion feeds the eight orchestrator stages; the two extraction branches of stage~2 run in parallel and are reconciled in stage~3. The LoRA layout adapters (dashed) are selected in stage~1 and evaluated as a standalone layout component.}
    \label{fig:system_architecture}
\end{figure*}

\textbf{Problem formulation.} Given a native or scanned PDF and a schema of typed fields with descriptions and constraints, supplied or retrieved from a registry, the system outputs field--value pairs that satisfy the constraints, are traceable to the document, are reconciled by a deterministic rule set and carry a confidence in $[0,1]$.

\textbf{Orchestration.} Fig.~\ref{fig:system_architecture} shows the eight stages. They share a state holding the document blocks, the rendered page images, the selected adapter, the extraction bundle of both branches, the fused fields and their audit records, the resolved schema, the validation outcomes, the storage key and any accumulated errors. Each stage handles its own exceptions, so a failure in one stage leaves a partial state that later stages can still use. The adapter group is selected from the identified or retrieved schema name; the adapters label layout regions, and the field extractors take spatial information directly from the OCR bounding boxes.

\subsection{Document Ingestion with OCR Fallback}

Ingestion turns a PDF into blocks, each with page number, text, bounding box $(x_0,y_0,x_1,y_1)$, confidence and a source tag (native or OCR). Native text is read with PyMuPDF; a page with fewer than 20 characters or five words is rendered at $2\times$ scale (halved above 5000 pixels) and passed to Tesseract, whose word-level confidences are kept for the fusion layer.

\begin{figure}[t]
\noindent\rule{\columnwidth}{0.6pt}\\
\noindent\textbf{Algorithm 1:} Deterministic field-level policy fusion\\[-4pt]
\noindent\rule{\columnwidth}{0.4pt}
\begin{algorithmic}[1]
\STATE \textbf{Input:} OCR-LLM value $v_O$, confidence $c_O$; grounded Donut value $v_D$, confidence $c_D$; floor $\delta$; field type $\tau$
\IF{$v_O$ and $v_D$ are both null}
    \STATE \textbf{return} null
\ELSIF{$v_D$ is null}
    \STATE \textbf{return} $v_O$ if $c_O \geq \delta$, else null
\ELSIF{$v_O$ is null}
    \STATE \textbf{return} $v_D$ if $c_D \geq \delta$, $v_D$ is usable and $\tau$ is not numeric; else null
\ELSIF{canonical($v_O$) $=$ canonical($v_D$)}
    \STATE \textbf{return} $v_O$ \COMMENT{agreement}
\ELSIF{field is spatially anchored}
    \STATE \textbf{return} $v_O$
\ELSIF{$v_O$ is unusable \AND $v_D$ is usable}
    \STATE \textbf{return} $v_D$ \COMMENT{evidence, not confidence}
\ELSE
    \STATE \textbf{return} $v_O$ \COMMENT{default}
\ENDIF
\end{algorithmic}
\vspace{-4pt}
\noindent\rule{\columnwidth}{0.4pt}
\end{figure}

\subsection{Parallel Extraction}

The Donut and OCR-LLM extractors run on two worker threads and return, per field, a value, a confidence and spatial metadata.

\textbf{Donut branch.} Each field $f_i$ is posed as a question $q_i$ derived from its description (e.g., ``What is the invoice date?''), giving $\text{answer}_i = \text{Donut}(\text{image}, q_i)$ with confidence
\begin{equation}
    c_i^{\text{donut}} = \frac{1}{T} \sum_{t=1}^{T}
    \max_{v} \text{softmax}(s_t)_v ,
    \label{eq:donut_conf}
\end{equation}
where $s_t$ is the logit vector at generation step $t$ of $T$. Weights are loaded lazily on first use.

\textbf{OCR-LLM branch.} A text LLM receives the first 4000 characters of the document and all field descriptions and returns a JSON extraction. Each field left empty is then passed with the page image to a VLM, which recovers values that depend on the image, such as stamps, tables and signatures. Extracted values are matched to OCR blocks to obtain their bounding boxes.

\subsection{Evidence-Based Policy Fusion}
\label{sec:fusion}

Donut's token probabilities are poorly calibrated: we observed 0.9--1.0 for both correct and incorrect answers. The fusion layer therefore decides from evidence and uses confidence only as a floor $\delta$ below which a lone value is discarded.

\textbf{Grounding.} Each Donut answer is searched in the OCR blocks of its page. An answer found in no block is dropped; a supported answer takes the confidence of the block that contains it.

\textbf{Usability.} A value is unusable if it does not parse as its field type (a date without a four-digit year, a non-numeric amount), if the same value was assigned to several fields, or if it is a clause of more than ten words rather than a value.

\textbf{Decision.} The OCR-LLM value is the default, and Donut takes over only when the OCR-LLM value is unusable and its own value is usable. Spatially anchored fields (dates, amounts, signatures) keep the OCR-LLM value on conflict. A Donut value may fill a field the OCR-LLM branch left empty only for non-numeric fields, because Donut-only numeric fills were the main source of wrong values in development. Algorithm~1 gives the per-field procedure.

Fusion also normalizes values (whitespace, punctuation and boilerplate such as ``as defined herein'') and runs cross-field checks such as $\text{effective\_date} \leq \text{expiry\_date}$ and $\text{disclosing\_party} \neq \text{receiving\_party}$. Failed checks are flagged in the record metadata, not silently corrected. Each fused field is stored with its source branch and the rule that selected it.

\subsection{LoRA Adapter-Routed Layout Analysis}

\textbf{Dataset grouping.} Four datasets with token- or region-level layout annotations form two groups by document style: Group~1 (receipts and invoices: CORD and SROIE, 1{,}363 training pages) and Group~2 (forms and multi-domain pages: FUNSD and DocLayNet, 4{,}954 training pages with DocLayNet capped at 5{,}000). Their layout statistics differ, so each group gets its own adapter on a shared frozen LayoutLMv3-base. A router keeps the base model and a few recently used adapters in memory and switches between them with the PEFT calls \texttt{load\_adapter} and \texttt{set\_adapter}. The adapters predict layout classes, not field values, so their training data does not leak extraction answers into Section~\ref{sec:res_e2e}.

\textbf{Unified label space.} The datasets differ in granularity: word-level entities in FUNSD, region categories in DocLayNet and receipt fields in CORD and SROIE. All are mapped to six labels: paragraph, heading, list item, table, caption and other. Each OCR token, with its box normalized to $[0,1000]$, receives the label of the first annotated segment that contains its centre point, or the background label otherwise. This turns word-, region- and document-level supervision into one token-level task and makes the two adapters directly comparable: because they share the base model and the label set, either adapter can label any document without retraining, which the cross-group evaluation uses.

\textbf{Adapter configuration.} LoRA is applied to the query, key, value and output projections with rank $r=16$, $\alpha=32$ and dropout 0.05. Training uses AdamW (learning rate $5\times10^{-5}$, weight decay 0.01), a cosine schedule with 6\% warmup, mini-batch 2 with 8 accumulation steps (effective batch 16), 512-token inputs, bf16 precision, at most 10 epochs and early stopping on validation macro-F1 with patience 3. Every run writes its full configuration, per-epoch metrics and test metrics to JSON files, from which all tables and figures in Section~\ref{sec:res_lora} are generated.

\subsection{Schema Registry, Validation and Storage}

Each schema is stored as the averaged all-MiniLM-L6-v2 embedding of its field descriptions and retrieved by cosine similarity with threshold $\sigma$. Below the threshold, a schema agent (GPT-OSS-120B/20B) matches fields, normalizes names or synthesizes a new schema; the same agent repairs fields that fail validation. Validation checks type and value constraints; an invalid field is retried or set to its schema default. Valid records are stored in SQLite.

\section{Experimental Results and Evaluation}
\label{sec:eval}

\subsection{Experimental Setup}

All experiments ran on a Windows~11 laptop with Python~3.12, PyTorch and one NVIDIA RTX~5060 Laptop GPU (8\,GB). Orchestration uses LangGraph and LangChain, fine-tuning uses PEFT, and storage uses SQLite.

\textbf{Layout adapters.} Each configuration was trained with seeds 13, 42 and 1234 on a fixed train/validation split: the datasets' own validation splits where they exist (CORD, DocLayNet) and a seeded 10\% hold-out otherwise (SROIE, FUNSD). Official test splits were used only for final evaluation: CORD (100) and SROIE (347) pages for Group~1, and FUNSD (50) and the first 834 DocLayNet test pages for Group~2. The baseline freezes the whole backbone and trains only the token-classification head, with the same data, seeds, schedule and early stopping.

\textbf{End-to-end extraction.} We evaluate on a seeded random subset of 100 SROIE test receipts (company, date, address, total), a seeded subset of 50 CORD test receipts (six amount fields) and a 15-document synthetic multi-page set (invoices, NDAs, employment contracts, land deeds and tender instruments; 30 fields). Subsets are drawn once from the official test splits with subset seed 0, and no setting was tuned on them. All model stages run locally at temperature 0: Donut-base fine-tuned on DocVQA, Llama~3.2~3B for the text pass, and Qwen2.5-VL-7B served by Ollama (8192-token context) for the vision fallback and as the VLM-only baseline. F1 is field-level token-overlap F1 after normalization, and EM is the share of gold values matched exactly. Code, result files and figure scripts are available at github.com/AyushK0808/multiagent-form-schema-etl.

Table~\ref{tab:ablation} identifies grounding as the decisive component: removing it costs 0.031 F1 on SROIE and 0.011 on CORD, and on SROIE it lowers the median per-document F1 from 0.850 to 0.788 and nearly doubles the share of receipts scoring 0.5 or less (8\% to 14\%). Because every fused value records the rule that selected it, the differences between the pipeline and its OCR-LLM branch can be attributed exactly (Table~\ref{tab:perfield}). On CORD the fused pipeline is at or above its branch on every field and equals the VLM on subtotal, tax, total and cash. There the policy changes six values: five become correct (one corrected cash amount and four amounts filled in) and none becomes wrong. On SROIE it changes 21 of 400 values. Six become better (three company names, two totals, one address) and one is unchanged in score. The other 14 are all addresses, and every one of the 15 address overrides is triggered by the same rule: Malaysian addresses often exceed ten words, so the clause test marks the correct OCR-LLM value as unusable and a shorter Donut fragment replaces it. The SROIE gap between the pipeline and its branch is thus caused by a single rule, which the log identifies directly; restricting the clause test to clause-type fields is a one-line policy change. We report the numbers obtained with the policy as fixed before testing.

Fig.~\ref{fig:halluc} breaks down the CORD hallucination rate, which is similar for all systems (0.148 for the pipeline, 0.151 for the OCR-LLM branch and 0.135 for the VLM). It is an annotation effect: subtotal accounts for 18 values in every system, and for the VLM 16 of its 18 subtotals copy another gold field of the same receipt, usually the total, on receipts that print no subtotal line. Excluding subtotals, the VLM's rate falls to 5.6\%. CORD also shows the dependence of grounding on OCR coverage: Tesseract returns about 11 text blocks per CORD receipt, against 29.5 on SROIE, so grounding removes nearly all of Donut's answers (about six per receipt before grounding), and the Donut-only and text-pass rows of Table~\ref{tab:e2e_aggregate} measure OCR coverage rather than those models. A stronger OCR engine directly increases what grounding can retain.

\subsection{Latency}

We timed 15 documents (five per dataset, after one discarded warm-up) with response caching disabled, running the stages one after the other; Fig.~\ref{fig:latency} reports medians. Fusion takes under 3\,ms and OCR about 1.2\,s. On SROIE, where the text pass fills most fields, the whole pipeline needs 14.3\,s per receipt against 19.5\,s for a standalone VLM call. On CORD, where sparse OCR forces the vision fallback, the pipeline median is 29.7\,s, and on the multi-page synthetic documents 24.4\,s, of which Donut accounts for 17\,s. Running the two branches concurrently, as in deployment, bounds the extraction time by the slower branch instead of their sum.

\subsection{Schema Registry Retrieval}
\label{sec:res_schema}

\begin{figure}[t]
    \centering
    \includegraphics[width=0.7\columnwidth]{schema_registry}
    \caption{Precision and recall of schema retrieval across cosine similarity thresholds $\sigma$ (50 labelled queries, eight registered schemas).}
    \label{fig:schema_pr_curve}
\end{figure}

The registry holds eight schemas: the four synthetic document types, SROIE and CORD receipts, purchase orders and forms. The query set has 50 labelled field-name sets. Forty belong to a registered schema (exact names, synonym renames, subsets, and subsets with unrelated extra fields; five per schema), and ten describe unregistered document types and must be rejected. At the operating threshold $\sigma=0.70$ (Fig.~\ref{fig:schema_pr_curve}), precision is 1.00 and no unregistered query is accepted, with recall 0.575; queries below the threshold go to the schema agent instead of being matched to the wrong schema. Precision stays high over a wide range: at $\sigma=0.45$ it is 0.889 at recall 0.800, still with no false acceptance, and false acceptances begin only at $\sigma=0.40$. A deployment that prefers fewer agent calls can therefore lower $\sigma$ substantially without accepting the wrong schema.

\subsection{Scope}

The public benchmarks are receipt subsets (100 and 50 documents) with four to six fields, evaluated in one run per configuration, so differences under 0.02 F1 are not resolved at this sample size. The multi-page set is synthetic and was written by the authors. Qwen2.5-VL may have seen receipt corpora during pre-training. The layout adapters are evaluated as a layout component; using their region labels as features for field extraction is the next integration step.

% -----------------------------------------------------------------------
%  V. CONCLUSION
% -----------------------------------------------------------------------
\section{Conclusion and Future Work}
\label{sec:conclusion}

We presented a schema-aware framework that reconciles an OCR-free and an OCR-grounded extractor field by field with a deterministic, evidence-based policy, together with a schema registry and style-specific LoRA layout adapters. The adapters improve test macro-F1 over a frozen backbone to 0.774 and 0.739 at 0.94\% trainable parameters and 4.5\,MB each. End to end, the pipeline reaches 0.980 F1 on a multi-page synthetic set, above a 7B VLM; it improves on its strongest branch on CORD and matches the VLM's exact-match rate there; and grounding OCR-free answers in the page text is its most effective component and keeps hallucinated values in check. The per-field audit record turns error analysis into rule analysis: the SROIE regression traces to a single clause-length rule. Future work will add the VLM as a third evidence source in the policy, restrict the clause test to clause-type fields, use the layout adapters' region labels in field extraction, replace Tesseract with a stronger OCR engine, evaluate on long multi-page contracts with public annotations, and extend the adapters to multilingual documents (e.g., XFUND).
